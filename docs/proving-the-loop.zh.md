2026 年 8 月 30 日，自愈闭环在无人看管的情况下三次修好了一个真实缺陷，且每次都从闭环之外得到验证。
本页记录这需要什么、证明了什么，以及运维必须知道的两件事：**修复先到生产、后到 `main`**，以及
**金丝雀永远不可能是验证闭环的那个对象**。

## 闭环从未真正被测试过，而且没人注意到

所有真实组件都通过自己的契约检查 —— `gaia`、`oracles` 和枢纽扫描全清，这正是把它们仔细建好的目的。
于是语料库里唯有金丝雀的发现，而金丝雀是一个宣告契约又故意破坏它的装置。

五次自主修复尝试一直被读作模型失败。并不是。它们被要求修改的文件 `momus/canary/canary.py` 开篇便写着：

> 一个故意不合规的服务……一个宣告契约然后明知故犯地破坏它的服务……**有两件事必须始终为真，二者都对诚实起承重作用。**

一个谨慎的模型读到这里会拒绝——并说明理由。那些拒绝每一次都是对的。而那些**确实**产出了代码的尝试
才是更糟的答案：它们跨过了一条被写明的不变式。

**金丝雀在结构上不可能成为源码级修复的靶子。** 它的修复是一个运行时开关（`POST /canary/fix`
翻转 `STATE["fixed"]`），恰恰因为源码级修复会让它永远合规，从此再也演示不出任何发现。修好金丝雀
就等于销毁金丝雀。

## PRAXIS —— 缺失的靶子

`praxis/praxis.py`，端口 9460，仅回环，无消费者，未联邦。一个文件，一个真实的源码级缺陷，以及一段
明确告诉它的主要读者——模型——修好它才是本意的文档字符串。

缺陷不是编造的：它在 `json.dumps` 之上签名，而不是在互操作规范形式之上。这正是每一次自主尝试在看不到
契约时所伸手抓的那个错误，也是当预言机那份 `manifest_canonical` 落后于枢纽第五个字段、导致所有预言机
清单验签失败时，生态真正经历过的那个错误。

它的测试被设计为**在演练进行期间失败**——缺陷下四中三失败，修复后四中四通过——而部署手以
`SKOPOS_AGENT_REQUIRE_TESTS=1` 运行它们，因此判定修复是否为真的正是这道关卡。一个靠重新发明规范形式
来满足探针的补丁，过不去。

### 如何进行一次演练

```bash
# 1. 故意弄坏它 —— 用一次提交，而不是开关
#    （把 praxis/_signature_payload 改回 json.dumps 并推送到 Gitea）

# 2. 让 MOMUS 看见两次；自动驾驶的轮值每 900 秒自己会做
curl -X POST http://127.0.0.1:9410/scan -H "x-momus-operator: $TOK" \
     -H 'content-type: application/json' -d '{"target":"praxis"}'

# 3. 等自动驾驶，或者手动派发
curl -X POST http://127.0.0.1:9410/remediate -H "x-momus-operator: $TOK" \
     -H 'content-type: application/json' -d '{"finding_id":"<id>"}'
```

接线分布在四处，四处都必需：只登记在其中三处的靶子，要么没人扫描，要么没人修复。

| 位置 | 内容 |
|---|---|
| `web/backend/services/remediation_fix.py` | `DEFAULT_SCOPE["praxis"]` —— 允许改动哪个文件 |
| `skopos/skopos/remediation/recipes.py` | `_PRAXIS` —— 如何构建，及其测试阶段 |
| `skopos/skopos/remediation/autopilot.py` | `DEFAULT_POLICY` 与 `DEFAULT_SCAN_ROTA` |
| 主机 | `/etc/skopos-deploy-hand/praxis.env`，以及 momus-backend 上的 `MOMUS_EXTRA_TARGETS` |

**主机压过代码。** 环境文件里的 `AUTOPILOT_SCAN_ROTA` 会覆盖 `DEFAULT_SCAN_ROTA`，只加进源码的靶子
永远不会被扫描。自动驾驶在启动时会打印自己的轮值表——这是这个问题唯一被抓到的原因。

## 已经证明的部分

三次演练，每次都从闭环之外验证：从验证者容器里、用另一把密钥、按 `oracle_core` 的规范形式重算清单签名。

| 派发 | 补丁作者 | 用时 | 结果 |
|---|---|---|---|
| 10:06 手动 | 普通修复器 | 3 分 29 秒 | 已部署，就地验证 |
| 10:17 手动 | **METIS 议会** | 10 分 11 秒 | 已部署，就地验证 |
| 10:51 **自动驾驶** | 普通修复器 | 3 分 26 秒 | 已部署，就地验证 |

第三次回答了「是否自动修复缺陷」。服务在 10:32 被弄坏，此后无人触碰任何东西：MOMUS 在自己的轮值中
发现了回归，自动驾驶按自己的时间表派发，整条链一直走到经过验证的部署。

三次的补丁都是对的——它**导入**了规范形式，而不是重写：

```diff
-    return json.dumps(manifest, sort_keys=True)
+    return _signer.manifest_canonical(manifest)
```

### 仍未证明的部分

议会作为**救援**。它写出过一个成功上线的补丁（第二次演练），但从未救回一个普通修复器已经失败的任务
——所有演练都在第一次尝试就成功了。要证明这一点，需要一个足够硬的缺陷，让第一、二次尝试老实地失败。

## 修复先到生产、后到 `main`

这是让人意外的部分，而且是刻意的。

指挥者把补丁提交到 `momus/fix-<finding_id>-<n>`，舰队**从那个分支提交**构建镜像，部署手把它晋级。
于是运行中的服务带着修复，而 `main` 仍带着缺陷。摘自 `git_push.py`：

> **只走分支，绝不 main，绝不 force。** 被盗凭据在这里能做的最坏的事，就是创建一个没人合并的分支。

其背后还有第二道独立策略：指挥者用**部署密钥**推送，而本仓库 `main` 的保护里
`push_whitelist_deploy_keys` 为假。无论代码怎么说，服务器都会拒绝该密钥推到 `main`。

### 需要记住的后果

**任何从 `main` 的重新构建都会静默地回退修复。** 这不是假设：上面每一次演练就是这样重置的——从 `main`
执行 `docker compose build praxis`，无需任何破坏动作。「闭环修好了」与「你合并了」之间的间隔，就是一个
普通部署会撤销修复的窗口。

### 如何合并

```bash
scripts/pull_momus_fixes.sh           # 拉取、校验、汇报。什么都不合并。
scripts/pull_momus_fixes.sh --merge   # 合并它刚刚放行的
scripts/pull_momus_fixes.sh --json    # 机器可读
```

`--merge` 只放行**除 `.momus/*.json` 之外什么都不碰**的分支——那是只追加的溯源记录，不改变任何行为。
触碰代码的分支会进入队列并被报告，因为 MOMUS 签名的「已修复」裁决证明的是发现停止复现，而不是补丁好。

运行时的两点提醒：

* **队列里大多数分支绝不该合并。** 演练之后队列里有 89 个，其中 84 个是金丝雀尝试：给一个必须保持
  损坏的装置打的补丁。合并它们会终结金丝雀的用处。
* **`git diff main..branch` 看起来会很吓人。** 一个在你近期提交之前创建的分支，会把那些提交显示为删除，
  因为 diff 比较两个状态，而合并取二者的并集。在相信它之前用一次演练确认：

  ```bash
  git merge --no-commit --no-ff momus-fixes/<分支>
  git diff --cached --stat HEAD     # 合并实际会产生什么
  git merge --abort                 # 如果只是看看
  ```

  PRAXIS 的合并就是这么做的：diff 声称四个文件里删了 447 行；合并实际产生一个文件，加五行、减九行。

### 实验性自动合并

指挥者上的 `SKOPOS_EXPERIMENTAL_AUTO_MERGE=1` 允许它自己合并一个经过验证的修复。默认在所有地方关闭，
并且在构造上就很窄：

* 只针对到达 `DONE` 的任务——已构建、组件测试通过、候选已过关、两个签名均已验证、已部署，并**就地**
  确认发现消失；
* 只针对修复前缀下的分支，因此无法被瞄准到任何人的工作上；
* `--no-ff`，使结果是一个可回退、且以其发现命名的提交；
* 遇到冲突就中止，默认分支保持不动；
* 绝不 `--force`。

**它在生产上已启用，且处于惰性状态。** 服务器拒绝部署密钥：

```
remote: Gitea: Not allowed to push to protected branch main
! [remote rejected]   HEAD -> main (pre-receive hook declined)
```

要让它真正生效，需要仓库所有者的一个刻意动作。把那一把部署密钥加入 `main` 的白名单是窄的选项：一个
仓库、一把密钥，在 Gitea 里一个开关即可回退。账户令牌也能奏效，但宽得多：Gitea 令牌是用户级的，它会
触及该账户拥有的**所有**仓库。

回退方式始终有两条：取消该变量；以及 `git revert -m 1 <提交>` —— 该命令就写在合并提交自己的消息里。

## 闭环逐步拆解

下面每一步都是一个拒绝点。无法作答的一步会让闭环停下而不是猜测，任务则留给人。

| № | 谁 | 发生什么 | 在这里被什么拦住 |
|---|---|---|---|
| 1 | MOMUS | 按自己的轮值（900 秒）扫描一个靶子，并用扫描密钥签署发现 | 没有策略条目的靶子只记录，永不派发 |
| 2 | MOMUS 验证者 | **第二个实例、独立密钥**重跑探针，并把契约与协议参考交叉核对 | 两次解读不一致 → `inconclusive`，该发现不构成证据 |
| 3 | 自动驾驶 | 决定是否派发：严重度、观测次数、冷却、每日上限 | 审计者、付款方与指挥者在永久拒绝清单上 |
| 4 | AI-Factory | 在已声明的 1–3 个文件范围内写补丁 | 凭据与闭环自身的裁判不可读；新增依赖被拒 |
| 5 | 指挥者 | 提交到 `momus/fix-<id>-<n>` —— 绝不 `main`，绝不 `--force` | 非快进的分支留给人处理，而不是强推 |
| 6 | 节点代理 | 从该提交构建镜像，并运行**组件自己的测试** | 套件失败会在任何关卡之前阻止构建 |
| 7 | 节点代理 | 启动候选容器，不发布任何端口 | 起不来的候选本身就是对补丁的裁决 |
| 8 | MOMUS | 对**候选**重跑探针，而非对运行中的服务 | 仍然复现 → 拒绝部署 |
| 9 | 指挥者 | 签署携带 MOMUS 裁决的部署指令 | 代理校验两个签名以及候选与线上的绑定 |
| 10 | 节点代理 | 按**自己本地**的服务白名单晋级镜像 | 名单之外的服务被拒；调用方无法扩大它 |
| 11 | MOMUS | 部署之后就地重跑探针 | 出现回归立即回滚 |
| 12 | 断路器 | 统计部署、回滚与连续失败 | 反复折腾一个服务会被节流，而不是重复 |
| 13 | 你 | 合并分支 | —— |

第 13 步是唯一由人完成的一步，下一节说明取消它需要什么。

## 剩下的事：把指挥者的密钥加入白名单

自动合并已建成、已在生产启用，且处于惰性。推送之前一切正常；服务器在最后一寸拒绝：

```
remote: Gitea: Not allowed to push to protected branch main
! [remote rejected]   HEAD -> main (pre-receive hook declined)
```

这不是要在代码里修的缺陷。这是 Gitea 的分支保护，也是设计所要求的两道独立策略中的第二道——第一道
是代码自身的拒绝：「只走分支，绝不 main」。

**需要加入白名单的密钥**，免得去猜是哪一把：

```
SHA256:aiTxt4Fy0PAtQXx6f8eCt38EUswyeQmVbPHP2Y9DwJU
skopos-remediation-conductor@oracle-host
```

**位置：** Gitea → `aicom` 仓库 → Settings → Branches → `main` 保护规则 → 勾选
**Whitelist Deploy Keys**。一个仓库、一把密钥、一个复选框。

**会改变什么。** 指挥者可以自己把修复落到 `main`，上面的第 13 步随之消失。闭环其他部分毫无变化：
代码守卫在其他所有路径上仍然拒绝 `main`，合并仍是 `--no-ff`，遇冲突仍中止，且仍绝不强推。

**代价是什么。** 今天被盗的指挥者凭据只能创建一个没人合并的分支。之后它就能写入 `main`——
**仅限本仓库**，因为部署密钥是按仓库生效的。账户令牌同样能解除这道拒绝，但宽得多：Gitea 令牌是
用户级的，会触及该账户拥有的所有仓库。请优先选择部署密钥。

**回退。** 取消勾选，或取消 `SKOPOS_EXPERIMENTAL_AUTO_MERGE`，或
`git revert -m 1 <提交>` —— 该命令就写在合并提交自己的消息里。三者任一即可。

## 在验证过程中新增的关卡

每一条都是靠观察闭环发现的，不是靠读它的代码。

**修复器能读仓库里的每一把密钥。** 整个单体仓库都挂载给它——根目录 `.env`、
`data/secrets/git-credentials`、一把供给方密钥、两把 JWT 签名密钥。写入侧有拒绝清单和已声明范围；
读取侧只有一个正则。现在是：按路径拒绝、从内容中清除密钥材料、拒绝审计者与指挥者自身的源码、容器内
遮蔽，以及一份统计「还能看到什么」的自查。当前为零。

这份自查立刻抓出了守卫在另一个方向上过于粗糙：二十个「凭据」，其中十九个是 ARGUS 的源码——
`keystore.ts`、`wallet.js`。`wallet.json` 是钱包；`wallet.ts` 是读钱包的代码。一个拒绝源码的守卫会被
不断放宽，直到什么都不再保护。

**没有任何环节运行被修复组件自己的测试。** 唯一的关卡是重跑一次探针，因此补丁可以满足探针、打断测试
套件，然后照样上线。现在 Dockerfile 里有一个 `test` 阶段——不是默认目标，所以 pytest 永不进入生产——
在其他任何人查看这次构建之前，无网络地运行覆盖被改模块的套件。

验证这道关卡时翻出了更糟的事：GAIA 的证明测试用**同一个**函数签名与验签，因此把 `reading_canonical`
换成 `json.dumps` 后那 39 个测试照样全绿。线格式现已用字面量钉死。

**闭环没有独立裁判。** `momus.engine.verify.Verifier` 写好了却从未被实例化，因此没有任何东西写入
「已确认」裁决，「同一探针触发了两次」便默认成了全部关卡——不是谁的决定，只是缺了裁判之后剩下的东西。
把它接上又发现了七个缺陷，其中两个危险：它把 Metis 的「我自己的回答通过了我自己的评审」标志读作
「发现已确认」——于是任何格式良好的回复都成了确认，包括正文说该发现**不**复现的那种——而且一份裁决会
**取消**观测次数门槛，那会让单一模型回答压过枢纽三次观测的保守设定。

它的第一个真实裁决同样是**错的**：它以 0.92 的置信度否定了一个确实验不过的签名。确定性契约探针如今
不在语言模型的职权范围内：它们交给持有独立密钥的第二个 MOMUS 实例去**重跑**探针，其答案再与协议自身
的一致性参考实现交叉核对——即对契约的第二次解读，好让探针本身的错误被抓住，而不是被确认两次。

**没有任何东西记录给模型看了什么。** 任务保存了答案而没有保存问题，而「模型错了」和「给模型看错了东西」
症状完全相同。现在每一次交互都落到 `/data/remediation_exchanges.jsonl`，包括拒绝。

## 演练与生产共用一份预算

值得直说，因为它在一天里造成了四次中断：闭环里没有任何东西区分演练与真实工作。自动驾驶的每日上限、
它的派发日志、以及断路器的按组件部署节流，都把演练算作生产。

风险不在于麻烦。而在于：测试了一整天之后的第二天若发生真实事故，它遇到的守卫预算早已花光——保护恰好
在需要它的时刻失效。解法是在派发记录上加一个「演练」标记，并让两套计数器彼此分开；这项还没做。
