# 是什么拦下一个坏补丁 —— 无人值守的修复要经过的那些防护

> 🌐 [English](autonomous-repair-guards.md) · [Русский](autonomous-repair-guards.ru.md) · [Español](autonomous-repair-guards.es.md) · [Français](autonomous-repair-guards.fr.md) · **中文**

> **端到端已验证** —— 训练靶子、三次演练，以及修复为何先到生产、后到 `main`：[proving-the-loop.zh.md](proving-the-loop.zh.md)。

**2026-08-29**，闭环走完了一个周期，中间没有任何人：自动驾驶按自己的排期在 13:58:33 派发，MOMUS
在 14:02:15 确认修复已经就位 —— 3 分 42 秒，一个真实容器被替换，并由闭环之外的核验坐实：一次
超出上限的未付费调用回答的是 `402` 而不是 `200`。

走到这一步，中途停了十六次，每一次都各自独立。没有一次是靠读代码看出来的；它们全都是因为某趟
运行卡住了才现身。本页就是这十六次各自变成了什么 —— 一个补丁如今要经过的那些防护，按它遇到
它们的顺序排列，以及每一道背后的那次事故。请把它当作两个问题的答案，运维迟早会问：*是什么拦下
了一个坏补丁*，以及*我的修复为什么停了*。

贯穿全篇的一条：**没有被证明确实修好了那件事的东西，一律不上线。** 连续八次运行里，闭环一次也
没有晋级过没通过自己闸门的补丁。下面的一切，要么就是这条规则，要么就是在走到它之前不白费一趟
运行的办法。

## 在一张工单被花掉之前

| 防护 | 它拒绝什么 | 为何存在 |
|---|---|---|
| **派发策略** | 清单里没有条目的组件，或严重度低于该条目的发现 | 遗漏是一种默认值，而默认值恰恰会被放宽后的配置在无人察觉时覆盖掉。被拒绝的组件（审计者、支付方、指挥者）是按名字拒绝的，而不是靠不在清单里。 |
| **时效性**（`AUTOPILOT_STALE_AFTER_S`） | 最近几次扫描已经复现不出来的发现 | `seen_count` 是累加的，从不下降，所以几周前就修好的 bug 会永远看起来像是证据。一个再也没人能复现的发现，是一个记性很好的已关闭 bug。 |
| **冷却**（对已终结的任务解除） | 往正在进行的工作上再堆工单 | 冷却保护的是正在进行的工作。已经升级出去的任务没有正在进行的工作，而在那之后仍能复现的发现，恰恰是值得再来一次的情形。重复次数由每日上限兜住，而每日上限才是应对「这东西一直失败」的正确工具。 |
| **退还**（`AUTOPILOT_RECONCILE_WINDOW_S`） | 把当天的预算花在没有任何人接手的工单上 | MOMUS 回 `200`，A2A 入口在接受的那一刻就回答「正在处理」，因为任务在后台运行 —— 这个回复说不出它后来怎么样了。自动驾驶会在一个时间窗内向指挥者确认：真的有工作开始了吗。若不设窗口地问，几小时后别人发来的一张工单会反过来给一张死掉的工单背书。指挥者不可达时一律不退还：退多了，上限就等于没有上限。 |

## 补丁正在被写出来的时候

| 防护 | 它拒绝什么 | 为何存在 |
|---|---|---|
| **利益冲突** | 触及 `momus/momus/`、`treasury/`、`skopos/` 或闸门自身的补丁 | 一个能给「判定发现是否属实」的东西打补丁的闭环，也能判定它不属实。在代码中执行，既比对作用范围映射，也比对模型的答复。 |
| **截断** | 在输出上限处被切断的答复 | `finish_reason` 一直在供应商的响应里，却没人读，于是一个最后那段三引号字符串从未闭合的文件被提交、构建并启动了。**即便残留的片段能解析通过，也照样拒绝**：截断是那份答复的属性，不是片段的属性。 |
| **语法** | 编译不过的补丁 | `ast.parse` 用毫秒回答的问题，容器启动要九十秒才回答 —— 而且回答成「候选实例没能启动」，一句听上去像基础设施故障的话，说的其实是一个被截断的文件。 |
| **依赖** | 该组件的构建并未声明的 import | Docker 构建只拷贝源码，所以一个新增了库的补丁能干干净净地构建出来，然后在 import 处死掉。这道防护会去读该组件的 Dockerfile / requirements / pyproject：「我可以打补丁的那些文件里没有 import 它」不等于「它没有装」。 |
| **空改动** | 什么都没改的补丁 | 在这种情况下报告成功，会推送一个空分支，并让 MOMUS 去闸门检查那个根本没打补丁的构建。 |

上面每一次拒绝都会**带进下一次尝试**。在 temperature 0 下，同样的提示返回同样的补丁，所以一次
不知道上次为什么失败的重试是重复，不是重试 —— 实测：八秒内三份一模一样的被拒 diff。

## 它上线的时候

| 防护 | 它拒绝什么 | 为何存在 |
|---|---|---|
| **用空闲的分支名，绝不强推** | 覆盖掉一条修复分支 | 被重开的任务按设计会重置自己的尝试次数预算，所以 `attempt` 不能拿来当唯一名字。分支名是对着刚取回的远端副本挑一个没被占用的；强推依旧被拒绝，因为一条已经分叉的修复分支，可能正有人在读。 |
| **晋级前闸门** | 晋级一个 MOMUS 未曾确认过的构建 | 探针是**对着候选实例**重跑的，所以一份「已修复」的裁决说的是那个即将上线的东西，而不是那个仍在运行、根本没打补丁的服务。 |
| **闸门就绪**（`SKOPOS_GATE_RETRIES`） | 把一个还在启动中的服务叫作「不可达」 | 「运行中」不等于「在监听」：容器一起来，智能体就回报构建完成。只有*不可达*才会重问 —— 一次拒绝，重问一遍还是同样地拒绝。 |
| **给不出结论的闸门不算裁决** | 因为闸门跑不起来就把责任归给补丁 | 再让工厂试一次，也修不好一个跑不起来的闸门；那样循环下去只会烧掉预算，然后升级出去、把责任推给那个修复。 |
| **智能体只部署它自己构建的东西** | 一份签名指令指名了并非该智能体产出的镜像 | 权限是刻意拆开的：指挥者发布指令，却无法执行它；智能体执行指令，却无法凭空造一份出来。 |
| **出现回归就回滚** | 让一次糟糕的晋级留在原地 | 部署后的复检跑在智能体回报**之后**，而不是之前 —— 一次和轮询间隔赛跑的复检，描述的是你本想替换掉的那个构建。 |

## 当它仍然修不好的时候

三次尝试，然后交给人。有两个杠杆决定这三次尝试值多少：

* **升级的是模型，不是计数器**（`AIFACTORY_REMEDIATION_ESCALATION_MODEL`）。从第 2 次尝试起，
  修复回合使用这里指定的模型。未设置就是由路由自己挑 —— 用同一个解不了这个问题的模型试三次，
  等于同一种失败发生三次，没有任何新信息。
* **把合约本身给它，而不是给一段对合约的描述。** 一个只说「你的签名验不过」却不说*签的是什么*
  的探针，等于是在要求别人照着一段散文重新实现一份互操作合约，而每一次尝试都实现得不一样。
  探针要写明自己的验收标准；凡是有共享库定义了合约的地方，服务就直接 import 它 ——
  复制出来的第二份，会在第一份新增一个字段的那天开始漂移。

## 仍然归人所有的事

* 针对安全内核的发现 —— 审计者、Treasury、闸门 —— 完全不走这条路。一个自我修复的审计者，
  等于给自己的工作签了合格证。
* 把修复分支合并进 `main`。一份 `fixed` 裁决上线的是一个镜像；它不合并代码。
* 一个组件的镜像里装了什么。闭环可以修镜像里的代码，但绝不可以自作主张添加依赖：
  那是一个供应链决定。
* 清除已跳闸的熔断器。代码中没有任何东西会清除它 —— 一个重启即复位的熔断器，
  恰会被它本要打断的那个崩溃循环击败。

## 本页引入的配置项

| 变量 | 默认 | 作用 |
|---|---|---|
| `AUTOPILOT_CONDUCTOR_URL` | `http://127.0.0.1:9402` | 只读，而且只用来回答一个问题：我们发出去的那张工单，有没有让任何工作真的开始？ |
| `AUTOPILOT_RECONCILE_WINDOW_S` | `600` | 一次派发要在多长时间内表现为真实的工作，超出则判定为被吞掉并退还。 |
| `AUTOPILOT_STALE_AFTER_S` | 扫描间隔的 `2 ×` | 超过这个时长仍未复现，该发现就不是一个活着的缺陷。`0` 关闭这项检查。 |
| `SKOPOS_GATE_RETRIES` / `SKOPOS_GATE_RETRY_DELAY_S` | `6` / `5` | 给一个智能体已经回报为运行中的候选实例留半分钟的启动余量。 |
| `AIFACTORY_REMEDIATION_ESCALATION_MODEL` | 未设置 | 从第 2 次尝试起使用的模型。把钱花在哪个模型上，是运维的决定。 |

## 值得留下的那条教训

十六次停顿里有三次并不是闭环的缺陷，而是**核验方式**的缺陷：一个本应把合约送到模型手里的修复，
看上去做完了三次，其实都没有，直到在接收端把真正的提示渲染出来才发现。一次构建检查跑在了错误的
检出上。一个观察器把一条旧的日志记录当成了新的。

**在接收端核实投递，绝不在发送端。** 上游的一切都可以看起来完全正确，而什么都没有送达。
